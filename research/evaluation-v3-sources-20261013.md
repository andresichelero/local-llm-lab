## Findings that affect the roadmap

- **Do not collapse benchmark names or versions.** These are separate things: SWE-bench Verified (the 500-task OpenAI curated set); Scale's SWE-bench Pro V2 (642 public tasks, plus HARD-51); and the September 2026 preprint/dataset SWE-Bench Pro Verified (731 refined instances, from the Pro task pool). Do not compare their scores as if one were a simple version of another.
- **“Held out” has at least two meanings.** A task can be withheld from an agent or scaffold developer while remaining public to model training. A network-denied sandbox blocks live retrieval; it cannot erase prior exposure in model weights. The public Pro V2 and Pro Verified releases include task data and reference-solution/test artifacts, so neither can be presented as guaranteed training-unseen for future models.
- **A score is model + harness + task distribution + verifier + budget.** METR explicitly recommends selecting the strongest available scaffold (or justifying the selection), tuning on a dev set, and inspecting task-level failures and run variance. A single un-tuned scaffold is not a clean estimate of a model's capability.
- **Isolation has separate channels.** Protect filesystem contents, Git history/refs, task metadata, network routes, and the reward/verifier channel independently. Terminal-Bench's current template uses a separate verifier container but defaults the environment to public internet; its review rubric warns that executing an agent artifact as root can let it forge a pass. “Containerized” alone is not an isolation claim.
- **Local implementation review found two additional baseline defects.** Timed-out agent/test descendants could outlive a killed leader, and guarded edits lacked full path confinement and a symlink-safe temporary-file path. Corrections are present through source checkpoint `2a58d61`; 286 pytest tests and 19 subtests passed, along with Ruff, compileall, and 41 shell syntax checks. Typechecking was unavailable. The focused safety subset and final scoped review were clean. The earlier retained review records a benign temporary-file reproduction but does not include exact raw stdout. This validates only tested runner paths; it does not establish OS isolation, process-tree telemetry, or inaccessible observer storage. See the [audit ledger and current-state addendum](../results/reports/methodology-audit-v3-20261013.md#current-implementation-status-addendum).
- **Local raw-data availability improved, but remains bounded.** A targeted top-level WSL2 inventory found 35 local-only Granite/Gemma admission and diagnostic files and hashed them into the index. Nested run directories were not traversed and file contents were not read; the records do not establish public availability or complete comparable run manifests.
- **Keep observation out of the control loop.** OpenTelemetry offers trace/event conventions for model and tool messages, but GenAI content capture is opt-in and parts of the event convention remain in development. For measurement, export traces to an evaluator-owned sink that the agent cannot read; do not send traces, grades, or monitor feedback back into a run unless feedback is the intervention being studied. The last sentence is a design recommendation inferred from the sources, not a guarantee provided by OpenTelemetry.
- **Editing interface can change results.** Aider documents whole-file, search/replace, unified-diff, and architect/editor modes and says models differ in format performance. Freeze the edit interface when estimating a model effect; if testing interface effects, make interface an explicit experimental factor and select/tune only on dev tasks.
- **Use several complementary measures.** EvalPlus shows why hidden/stronger tests can change correctness rates and rankings, but it evaluates function-level code generation rather than repository agents. Pair it with repository/terminal tasks and a small private confirmatory set. Report task-level pass/fail and failure categories, repetitions where runs are stochastic, and uncertainty across tasks; do not treat repeated trials on one task as independent tasks.

## Roadmap recommendations

1. **Record a reproducible run manifest first.** Pin model file/checksum and quantization, runtime/build, prompt, context and sampler settings, agent/scaffold version, edit format, tool permissions, task revision, verifier revision, time/token/tool-call limits, hardware/concurrency, seed, and all retries. This lets a result be attributed to its actual cause.
2. **Separate development from confirmation.** Iterate prompts, tools, and edit formats only on a public/dev split. Keep a small, privately authored confirmatory set from clean repository snapshots for final comparisons; keep issue instructions visible but tests, gold patches, future Git refs, and reward files outside the agent's view. Public Pro/Pro Verified releases can be useful protocol checks, but not guaranteed training-unseen tests.
3. **Use two comparisons.** First hold the harness fixed to estimate the model change. Separately compare a modest set of model-appropriate scaffolds/interfaces selected on dev tasks to estimate best practical performance. Report both; do not pick the winning interface after looking at confirmatory results.
4. **Make the verifier independent.** Start each task from a fresh image/worktree; remove future Git history and hidden artifacts; deny agent network access or explicitly allow only what the task needs; keep dependency caches prebuilt; run verification outside the agent container as an unprivileged process; protect reward output from agent writes; then replay the final diff against a clean image. Record which of these controls actually ran.
5. **Measure per task before aggregating.** Store task ID, repeated-run outcome, failure category, tests reached, time, tokens, tool/edit counts, and verifier reason. Show task counts and per-task pass rates, plus aggregate uncertainty resampled across tasks. Repeat selected tasks to expose stochasticity; do not inflate sample size by counting same-task repetitions as new tasks.
6. **Keep the observer passive.** Export tool/model events and timestamps to an evaluator-only sink; the running agent should not be able to read the trace or verifier state. Treat prompt/output capture as sensitive data and opt into it deliberately. If you later add monitors or feedback, run a separate experiment because that changes the evaluated system.
7. **Use external benchmarks as diagnostics, not the headline.** EvalPlus checks function correctness; SWE-bench Pro V2 checks repository issue resolution under a defined locked protocol; Terminal-Bench checks broader terminal work and may permit public internet. Report exact versions, harness, network policy, and task count beside every score.
