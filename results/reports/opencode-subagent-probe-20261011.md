# OpenCode subagent coordination probe — incomplete, SSD only

Date: 2026-10-11. Model: Qwen3.5-9B Q4_K_M, revision `3885219b6810b007914f3a7950a8d1b469d598a5`. OpenCode `1.19.0` called the configured `repo-explorer` subagent successfully. The child session returned findings to the primary agent, confirming that this local version can execute a real subagent tool call against the local llama.cpp endpoint. A bounded read-only delegation then returned the correct three test names in 14.25 seconds, with a `steps: 3` primary-agent cap accepted by the installed version.

The coding task did not complete. The unbounded attempt was stopped after six minutes. The primary had made a partial edit but had not called `independent-reviewer` or produced a final response. A second coding attempt with `steps: 6` finished in 65 seconds, but its final code passed only 1/4 tests. A third attempt with `steps: 14` ran for 143 seconds, passed 3/4 tests, but did not invoke a `task` subagent or the independent reviewer and still failed the no-space `512MiB` case. Both bounded coding attempts exhausted their step budget before the requested workflow completed. All three coding attempts are excluded from success-rate or speed comparisons.

The first launch was invalid because the shell-owned background server exited with its parent. The retry used `nohup`, persisted, and served the model. The unbounded retry used context 16,384, Q4_0 K/V, Flash Attention, 99 GPU layers, and temperature 0. `/usr/bin/time` reported 636,712 KiB maximum RSS for the OpenCode process; one GPU sample after model load showed 6,043 MiB used. llama.cpp logged a failed restore of 16,006 KV cells while changing prompt state, then continued with four server slots configured by default. The bounded attempts used one server slot and disabled prompt caching; the successful short delegation had 882,720 KiB maximum RSS, while the failed coding attempt had 750,924 KiB maximum RSS. These are per-process and single-sample observations, not stable peak estimates. The test supports using a bounded primary and one server slot for the next coding run, but six steps were not enough to complete the requested review cycle.

All model, runtime, temporary workspace, prompts, tests, events, and logs were on the C:-backed WSL ext4 SSD. No HDD benchmark I/O occurred. The exploratory summary and raw event streams are preserved under `results/raw/exploratory-invalid/`; full scratch files remain at `/home/foxtrot/local-llm-benchmark/results/opencode-subagent-probe-20261011` until this experiment series is ready for archival to E:.

The next controlled run should compare the existing OpenCode single-agent fixed coding task against the same task with one read-only explorer delegation and, only if the first stage completes, a second independent reviewer. Use a wall-time cap and measure a larger primary `steps` allowance; the local 14-step run still failed to invoke the reviewer. Keep all active I/O on WSL ext4 and exclude incomplete rows. The config template in `benchmark/configs/harnesses/opencode-subagents.json` uses ten steps as a starting point, not a measured optimum.

## Evidence and limits

- Completed: two local `task` tool calls and child exploration sessions, including one correct read-only result in 14.25 seconds; a `steps` cap was locally accepted.
- Not completed: coding task success, independent review, final quality gate, repeated valid measurements, matched single-agent control, context compaction, or stable resource sampling.
- Interpretation: local subagent compatibility is demonstrated only for a short read-only request. The coding runs had low task success and did not complete the review stage; no task-quality advantage is established. A step cap limits runaway work but needs calibration and did not make this coding task efficient.
- Research: current OpenCode documentation describes `subagent` agents, `subagent_depth`, and a positive `steps` limit. The installed `1.19.0` accepted `steps: 3` and completed the read-only delegation. [Agents documentation](https://opencode.ai/docs/agents/), [configuration documentation](https://docs.opencode.ai/docs/config/).
- llama.cpp documents tool calling through compatible Jinja templates and its server supports tool definitions when the tool-capable template is enabled. This server/model combination did successfully service the child requests; the earlier KV-state restore warning was nonfatal. [llama.cpp function-calling documentation](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md).
